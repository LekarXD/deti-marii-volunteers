# Вымышленные данные публичного демонстрационного контура

Это отдельная операторская команда для **пустой новой `opora_stage`**. Она не является
импортом фонда, обычным production bootstrap, HTTP endpoint или заменой проверки
входа. Исходники: `apps/api/app/stage_demo/`. Автоматически при запуске API не выполняется.

Контур: `https://www.odschool.ru/deti-marii/`, Compose project `opora-preview`, файл
`/opt/odschool/opora-preview/releases/<ПОЛНЫЙ_SHA>/infra/preview/compose.yml`, отдельная
БД и volume. Runtime: `OPORA_ENVIRONMENT=staging`, `OPORA_DEV_INBOX=false`, secure
cookies, отдельный криптографический ключ. Провайдеры внешних писем/Telegram не нужны.

## Что создаётся

- Шесть явно демонстрационных аккаунтов `*@example.test`: координатор, волонтёр,
  новичок и три дополнительных вымышленных участника состава. У исторического
  контакта CRM нет автоматически привязанного аккаунта.
- Свежий TOTP-фактор координатора. Он подтверждается обычным API при первом входе.
  Команда не создаёт `Session`, не ставит `mfa_at`, не копирует локальные cookie,
  сессионные токены или существующие TOTP-ключи.
- Текущая анкета из `FORM_VERSION` и актуальное знакомство из существующего
  `seed_introduction`: четыре модуля и финальный тест. Ответы анкет вымышлены;
  завершение знакомства и успешные оценки не подделываются.
- Группа из трёх вымышленных персонажей без фотографий и реальных характеристик,
  роли, две возможности, будущие и прошлые события, приглашённое/подтверждённое
  участие, общие резервирования времени, реальные записи минутного журнала.
- Добро.рф: статусы approved/applied/not_needed, общий пример 10 часов за день,
  ограниченный восемью часами, минутный остаток и вымышленная ручная отметка за
  прошлый месяц. Ссылки ведут только на главную `https://dobro.ru/`; CRM не открывается.
- Анкеты/контакты CRM, договорённость и следующее действие, окно собеседований и одна
  встреча, внутренний чат, рефлексия, вопрос координатору, черновик отчёта на реальных
  вымышленных фактах, онлайн-событие и авторские черновики базы знаний/тренажёра.

Эфир, готовое видео, успешный ИИ-разбор и публикация черновиков **не имитируются**.
Для них сохраняются реальные состояния доступности провайдеров и редакторские проверки.
Внешний outbox seed не создаёт. Изображения реальных подопечных и реальные контакты
не используются.

## Однократный запуск оператором

Сначала применить миграции и создать отдельный приватный каталог:
`/opt/odschool/opora-preview/private/demo`, владелец UID10001, mode0700. Только этот
каталог монтируется в API как `/run/opora-private`; основной `private/runtime.env`
остаётся доступным root. Ключ шифрования контура создаётся отдельно оператором.

Команда из подтверждённого frozen release (подставить его **полный SHA**):

```sh
docker compose --project-name opora-preview \
  --env-file /opt/odschool/opora-preview/private/runtime.env \
  -f /opt/odschool/opora-preview/releases/<ПОЛНЫЙ_SHA>/infra/preview/compose.yml \
  exec -T -e OPORA_STAGE_FIXTURE_SEED_ALLOW=true api \
  python -m app.stage_demo \
  --confirm ONLY_SYNTHETIC_OPORA_STAGE \
  --credentials-path /run/opora-private/demo-credentials.json seed
```

Разрешение передаётся **только этому exec-процессу**, не в окружение API/воркеров.
stdout содержит лишь статус и путь к файлу. `demo-credentials.json` записывается
с mode0600, без замены существующего файла; в нём свежий TOTP и manifest UUID.
Файл остаётся на сервере. Его содержимое не выводить в логи, чат или Git.

Проверки команды: точное имя БД `opora_stage`, staging runtime, выключенный dev-inbox,
secure cookies, явная фраза подтверждения, отсутствующие внешние провайдеры, пустая
первичная база аккаунтов и отдельное имя вымышленного фонда. Вся запись идёт одной
транзакцией; marker защищает от повторного добавления. Повтор с тем же приватным
файлом возвращает `already_seeded` и ничего не пересоздаёт. Если до commit случился
аварийный обрыв процесса и остался приватный файл без marker, повтор завершается
ошибкой; оператор отдельно проверяет состояние, не запускает reset.

## Обычный вход без публичного dev-inbox

1. Открыть страницу входа и запросить код на **один из вымышленных адресов manifest**.
   Это создаёт обычный AuthChallenge и зашифрованную запись email outbox. Почтовый
   провайдер не настроен, поэтому приложение честно не сообщает об успешной доставке.
2. Передать оператору публичный UUID именно этого запроса. Он выполняет тот же exec
   с подкомандой ниже. Команда допускает только точный вымышленный email, связанный
   с UUID созданного аккаунта, foundation и committed marker; проверяет срок,
   отсутствие использования и хеш обычного токена.

```sh
python -m app.stage_demo --confirm ONLY_SYNTHETIC_OPORA_STAGE \
  --credentials-path /run/opora-private/demo-credentials.json \
  login-token --email coordinator@example.test \
  --challenge-id <UUID_ОБЫЧНОГО_ЗАПРОСА> \
  --output-path /run/opora-private/login-<UUID_ОБЫЧНОГО_ЗАПРОСА>.json
```

3. Токен записывается только в **новый** приватный файл0600, stdout содержит путь и
   expiry. Оператор вводит его в обычную форму, затем подтверждает обычный MFA кодом
   свежего TOTP. `login-token` не подтверждает вход, не меняет попытки/сессии/MFA и
   не создаёт токены самостоятельно. Использованный или истёкший запрос отклоняется.

Публичные auth endpoints, Origin/CSRF, rate limits и MFA не изменяются. CLI не
используется для реальных email, других фондов или production БД. На сервере не
включается локальный dev-inbox и не появляется endpoint просмотра писем.

## Проверки исходников

`apps/api/tests/stage_demo/test_stage_demo.py` проверяет отказ неправильному runtime,
провайдерам и разрешению, mode0600/запрет замены/симлинков, реальное заполнение новой
локальной PostgreSQL `opora_stage`, идемпотентный повтор, отсутствие сессий/outbox
после seed и полный обычный HTTP-путь challenge → verify → MFA с выключенным
dev-inbox. Временные секреты теста остаются в приватных файлах pytest.

Серверные команды и браузерную приёмку выполняет владелец staging-развёртывания.
