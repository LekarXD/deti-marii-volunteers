# Messaging P17A contract

Include `router.router` once. All conversation data requires a current explicit member in the same foundation; staff permissions do not implicitly read unrelated threads. `messaging.manage` permits creating group conversations and modifying members only in a conversation that the actor already belongs to. Candidates may open a direct thread with an active coordinator. `/contacts` exposes display names only; unprivileged users see active coordinators only.

List: deterministic created-at/UUID cursor, max 50 conversations; history max 100 messages, sequence cursor; `/sync?after_seq` max 100, revision + unread + next sequence. UI polls selected history every 3 seconds and list every 7, stops in hidden tabs, caches at most five pages. Read cursors are monotonic and exclude own messages from unread. Send and membership commands have actor-bound durable receipts; membership authorization is repeated before receipt replay and after obtaining the conversation lock. Conversation lock serializes sends, membership revoke and sequence allocation.

Attachments must be current-owner, ready assets in the same foundation. Participant photo assets cannot be forwarded. After attach, generic asset owner access closes: only the linked conversation content route can resolve the file after fresh membership checks. Images require explicit `photo_policy=no_people`; there is no claim of detecting or blurring faces. UI explains photo restrictions and the unavailable blur processor. AI summary is likewise explicitly unavailable pending P15.

`consumers.enqueue_notice(db,foundation_id,recipient_id,subject,body)` enqueues an encrypted `in_app` envelope in the caller transaction. It is for authoritative already-authorized events, not audience selection or broadcasting. P06 emits `internal` with `{event,booking_id,booking_version}`: consumer locks and reads current booking, validates exact current version/state and derives the current recipient from the booking, never from stale envelope identity. Old reminders/changes are suppressed. Registration-only recipient delivery waits until identity verification; expired registration suppresses delivery. Other domain sources must add explicit source-specific validation, never send a stale snapshot through the generic notice helper. System messages are deduplicated by unique source outbox ID and saved atomically with job fencing/outbox state. System conversations cannot accept user replies.

P17B boundary: SMTP supports purpose-bound login challenge emails only. Development inbox never calls SMTP. Missing configuration is unavailable; a disconnected DATA response is unknown and is not blindly retried or presented delivered. No real external recipient was used in tests. Preferences/no-contact, marketing templates, webhook delivery confirmations, audience preview/broadcast and additional channels remain P17B follow-up; no API here claims them complete. SMTP state `delivered` means SMTP accepted, not proof the recipient read it.

P15 knowledge and RTC consumers can link a permitted conversation UUID as context, but must recheck membership at every read/send and keep private notes out of text. No service credentials inherit indefinite membership or publication rights.
