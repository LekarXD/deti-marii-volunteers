# Ручной перенос часов в Добро.рф

Опора читает подтверждённые минутные записи `service_time_entries`, созданные из
посещений. Журнал Добро.рф не меняет посещения, минуты, назначения или допуск.
Сервис не входит в CRM Добро.рф, не хранит её пароли и не сообщает об автоматической
доставке. Отметка координатора означает только его подтверждение ручного действия.

## Источники и границы внешних правил

Проверено 22 октября 2026 года:

- [Материал Добро.Медиа с ответами команды платформы](https://dobro.press/articles/kak-privlech-opytnyh-i-aktivnyh-volonterov-na-dobroe-delo-sekrety-ot-administratorov-platformy-dobrorf)
  подтверждает ограничение восемью часами в сутки, проверки пересечений и срок
  внесения после завершения мероприятия. Это обоснование расчётного дневного лимита.
- [Разъяснение об отсутствующих часах](https://dobro.press/articles/ne-podtverdili-volontyorskie-chasy-chto-delat)
  описывает необходимость отклика и его одобрения, сроки 30 дней на одобрение и
  60 дней на часы; верифицированные часы зависят от верификации организатора.
- [Официальная инструкция о проставлении часов](https://edu.dobro.ru/upload/uf/a86/tzrnpditoi16jgkb1vcxu9ug7rgfqv23.pdf)
  найдена в официальной выдаче; прямое получение PDF вернуло 503. Она не использована
  как доказательство поддержки дробных часов или накопительной суммы.

Не подтверждены внешним испытанием: целые/дробные часы, ввод накопительной суммы
длительного дела и его дневные проверки, реферальные контакты, наличие публичного
API, верификация конкретного фонда, универсальный срок модерации 7–14 дней.
Интерфейс не выдаёт эти предположения за результат проверки. Текущая рабочая
проекция готовит целые часы с сохранением минутного остатка; перед первым переносом
координатор сверяет правила в CRM. Сроки настраиваются. Флаг верификации изначально
выключен. Одноразовая подготовка предлагает опубликовать дело заранее, без обещания
срока модерации.

## Атрибуция и расчёт

`dobro_activity_links` привязан к возможности. Дата включается в один действующий
интервал; PostgreSQL `EXCLUDE` не допускает пересечение интервалов одной возможности.
`dobro_series_opportunities` явно связывает серию событий с возможностью. Нельзя
выводить такую связь из роли, названия или совпадения программы. После фактов участия
привязка серии сохраняется. До использования ссылку можно исправить с проверкой
версии; после отклика, переноса или связанного факта она закрывается для изменений.

Дневной лимит общий для всех явно связанных добрых дел одного человека. Не связанные
с Добро.рф посещения этот бюджет не расходуют. `not_needed` не меняет распределение
общего бюджета между делами: он исключает перенос своей строки. Порядок распределения:
начало события, затем неизменный UUID назначения. Часовой пояс — Москва, как в
существующем минутном журнале. Переход через полночь разделяет дни.

Источник хранит длительность, а не точные отметки входа/выхода. Поэтому фактические
минуты консервативно занимают начало события; пересечение с более ранним событием
исключается. В интерфейсе отдельно указаны минуты, ограниченные дневным лимитом,
пересечением и длительностью. Это не скрытая потеря минут: исходный журнал остаётся
без изменений.

Расчёт накопительный до конца выбранного месяца: `floor(eligible_minutes / 60)`.
Из него вычитается сумма подписанных часовых дельт журнала переносов. Остаток минут
сохраняется. Уменьшение исходного посещения может дать отрицательную дельту в следующем
периоде. Нельзя редактировать старый месяц после записи в более позднем; историческая
строка доступна для просмотра. Частичный перенос допустим только в направлении и
пределах актуальной суммы. Отрицательная запись требует причины.

## Подтверждение и конкурентные изменения

Сохранение требует явного подтверждения, права `hours.review`, актуальной сессии,
Idempotency-Key и хеша серверного снимка. Порядок блокировок: текущие права → журналы
минут людей по UUID → данные Добро.рф фонда. Это совпадает с порядком записи посещения
и её триггера, поэтому ручной перенос не создаёт обратную зависимость. Снимок пересчитывается
перед записью. Изменённый факт даёт 409; интерфейс сохраняет заметку и требует сверки.
Повтор одного ключа возвращает тот же результат, другой ключ со старым снимком не
создаёт вторую запись. Несколько строк подтверждаются одной транзакцией.

Перенос `applied` одновременно фиксирует `approved` и событие истории. Прямое
одобрение волонтёром запрещено. Отказ от Добро.рф никогда не отменяет назначение.
Профиль необязателен. Из карточки CRM используется только явная связь CRM UUID → User
UUID: контакт без аккаунта не сопоставляется по email и не становится помощником.

## Внутренние напоминания

Выключены по умолчанию. Координатор включает их в настройках; требуются актуальные
права `integrations.manage` и `hours.review`. `dobro.reminders.scan` планирует
ежемесячное напоминание и сигнал жёсткого срока. Используется только канал `in_app`.
В существующих durable receipts хранится ключ «получатель × месяц» либо
«получатель × доброе дело × жёсткий срок», исключающий повтор при ретраях.

NoticeSource заново проверяет владельца, настройки, MFA/права, актуальные суммы и
сроки при доставке. Отзыв прав или выключение настройки подавляет уже поставленное
сообщение. Внешние email/Telegram и напоминания волонтёрам автоматически не отправляются.
Кнопка «Напомнить» открывает редактируемый текст для ручного копирования.

Подключение корнем: router + model loader, `app.modules.dobro.jobs` в allowlist
воркера, `app.modules.dobro.notifications` в allowlist NoticeSource и IO manifest.
Миграции 20/21 централизованно пишет A1, не этот модуль.

## Проверки

`OPORA_DOBRO_TEST_DATABASE_URL` должен оканчиваться на `/opora_dobro_test`. Набор
проверяет реальный PostgreSQL и HTTP: общий лимит двух дел, исключение несвязанных
посещений, остаток, отрицательную коррекцию, applied → approved, конкурентное
идемпотентное подтверждение, изоляцию фонда, отзыв права, редактирование до фактов,
связь CRM с аккаунтом и worker → NoticeSource → внутреннее сообщение. Отдельные
тесты проверяют опасные URL, пересечения и переход через полночь. React-тесты
проверяют сохранение черновика при фоновом обновлении и конфликте версии.

Тесты создания metadata не заменяют миграционные проверки триггеров: A1 отдельно
проверил upgrade/downgrade и реальные ограничения append-only, диапазонов и связей.
Проверки в настоящем кабинете CRM Добро.рф не выполнялись.
