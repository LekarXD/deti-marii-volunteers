# Canonical staff administration

The existing core StaffMembership, PermissionGrant, MfaFactor, ContactChannel and Session remain authoritative. StaffInvitation stores a bounded grant intent and a hashed code, not a second identity or role store. A1 owns its migration and trusted email-purpose registry; this module registers staff_invitation.

Admin routes require current foundation staff.manage. Mutations re-read the actual session and require MFA within ten minutes before receipt replay. Actor/target authz advisory locks are acquired in sorted order; invitation delivery commands then acquire shared contact_guard before domain row locks. Member.version is User.authz_version. Existing grants/revoke routes accept optional expected_version for backwards compatibility; new UI must always send it. Versioned grant races return one success and one409. A receipt replay never bypasses renewed authorization.

GET /coord/staff returns StaffDirectoryView; /permission-catalog returns StaffPermissionCatalogView; /scopes and /user-options?q return actual bounded resource/verified-user choices. No arbitrary UUID scope or unknown permission is accepted. Foundation scope has null scope_id; group permissions, including report read/write/export, resolve current foundation groups; recording manage/review/publish remain separate foundation permissions; studio.host resolves current webinars. Program scopes are unavailable because there is no canonical program entity. Deprecated seed permission names without a current handler are omitted from the assignable catalog.

POST /coord/staff/invitations creates a72-hour default invitation (1–168 hours). GET lists canonical status/delivery; POST /{id}/revoke and /{id}/resend require expected_version. Resend rotates the code/version; older queued delivery is suppressed at source validation. Provider-unconfigured creates an honest unavailable status without enqueueing fake delivery. Known verified no_contact is honored at enqueue and dispatch, including canonical CRM aliases; volunteer topic opt-in does not authorize or suppress this administrative purpose. No external email is sent by tests.

POST /staff/invitations/accept receives {token} in JSON only, under the authenticated current user whose verified email exactly matches the invitation. Codes never appear in a response, URL, audit fields or receipt. Accept creates/reactivates an existing membership without applying new grants; revoked historical grants are not revived. State becomes accepted_pending_mfa and next_action identifies actual enroll/verify/finalize readiness. Existing POST /auth/mfa/enroll and /auth/mfa/verify perform the real factor workflow. Then POST /staff/invitations/{id}/finalize with expected_version requires a confirmed factor and fresh MFA, revalidates issuer/current scopes/contact/expiry and applies the approved grants atomically. GET /staff/invitations/{id} is recipient-only. Replayed, expired, revoked, wrong-contact and foreign-foundation codes cannot activate access.

Actual PostgreSQL tests use isolated disposable schemas and encrypted development outbox fixtures. The end-to-end factor test invokes the actual MFA enroll/verify endpoints before finalize; no public role switch or session-MFA flag shortcut exists in the product.
