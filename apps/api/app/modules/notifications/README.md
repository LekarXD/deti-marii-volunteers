# P17B delivery contracts

Mount `notifications.router.router` once alongside messaging. This module adds notification preferences, immutable template publications, expiring audience previews, durable outbox delivery attempts and provider-webhook verification. It does not send to external recipients merely by importing data or publishing a template.

Self preferences use a versioned command and a user-owned session. Email notifications default off. Effective no-contact combines the user's preference with the canonical CRM alias-aware opt-out. Requested account authentication emails remain separate; expired or consumed challenges are suppressed before sending. Automatic inbox, invitation and reminder events recheck the current policy under `core.contact_policy.contact_guard` before persistence. Writers must take that guard before CRM/booking/assignment locks.

Templates allow only literal text plus `{volunteer_name}` and `{foundation_name}`. Attribute access, conversions, format expressions and header newlines are rejected. An `in_app` template must fit one 8000-character message (subject, newline and body) with every field expanded to its 200-character maximum. Published revisions are immutable. Audience preview is a stored snapshot with a hash, actor, template revision and 15-minute expiry. Sending requires the exact preview/hash, explicit `confirmed: true`, `notifications.send`, CSRF and an idempotency key. Recipient preferences, contact availability and provider readiness are rechecked before enqueue; the delivery worker rechecks the sender's live session/grants and recipient policy again. A changed audience returns conflict, not partial success. API success reports `queued`, never delivered.

SMTP is a real adapter, with bounded timeouts, verified TLS when enabled, stable Message-ID and explicit accepted/rejected/unavailable/unknown outcomes. `accepted` means the SMTP server accepted the message. It is not a delivery/read receipt. Development inbox never opens SMTP. Missing provider configuration is unavailable. Before external I/O the worker commits a `calling` attempt marker. A crash or lost response leaves an unknown outcome; the next claim does not resend blindly. Unknown deliveries require operator review and a new explicitly confirmed command if a resend is appropriate. Journals expose state/codes/times only, not raw tokens, message bodies or recipient contact strings.

The generic optional webhook adapter uses an environment secret and HMAC-SHA256 over `timestamp + '.' + raw_body`; request timestamps must be within five minutes. Body is capped at 64 KiB. Event IDs are durable replay keys, conflicting replay payloads are rejected, and stale timestamps cannot regress delivery state. This is an explicit adapter contract, not a claim that an unconfigured third-party provider supports it. SMTP-accepted status cannot overwrite a stronger delivered/bounced webhook result.

Tests use invented accounts, actual local PostgreSQL, and a real temporary SMTP server bound exclusively to 127.0.0.1. No message is sent to a real recipient. Tests cover template restrictions, preference CAS, opt-out between preview/send, idempotent enqueue, internal persistence, real SMTP acceptance, interrupted calling→unknown without resend, signature/timestamp checks and webhook replay. Production provider connectivity, provider-specific webhook registration and browser UI acceptance remain separate environment gates.
