# Recording kernel

Projects, takes, current privacy projections, monotonic renderer fences, scene history, render/review/publication records use PostgreSQL and the shared asset/job lifecycle. The owner needs explicit `recordings.manage`; exact render approval and learning publication additionally require `recordings.review` and `recordings.publish`. Room membership belongs to `studio`, and immutable lesson versions belong to `learning`.

The private renderer uses a one-use opaque orchestration ticket (three minutes) in `Authorization: Bearer`. Bootstrap consumes it and returns an independent two-hour opaque renderer access credential. Both are stored only as hashes and are bound to the take, room generation and current host auth session. The orchestration handoff must put the bootstrap ticket directly in browser memory through a private init binding; URLs, fragments, cookies, history and ordinary app providers are not credential channels. No ordinary HTTP endpoint issues bootstrap tickets. A leased internal capture job must fence before issuing one.

Projection hashes use SHA256 of RFC8785/JCS UTF-8 bytes, with pinned [rfc8785.py](https://github.com/trailofbits/rfc8785.py). They cover exactly `{scene,capture_plan,resolved_assets}` and exclude credentials and transport fields. This preserves ECMAScript numeric serialization, including integral floats, negative zero and exponent boundaries. Authorized renderer reconnects use header-only `POST /api/v1/recording-renderer/provider-grant`; it returns a fresh least-privilege room grant with the current projection fence, or explicit unavailability.

Each scene, allowlist, privacy or asset change increments `renderer_state_version`, clears readiness and appends its exact projection/hash. Readiness requires that fence/hash, approved policy, exact asset checksums, only allowlisted tracks, required ready tracks and the actual 1920x1080/DPR1 renderer profile. Readiness receipts carry a strictly increasing per-grant `readiness_sequence`: delayed older receipts are rejected and identical retries retain the original expiry. Issuing a new bootstrap ticket revokes all older grants for the take, clearing readiness. Readiness includes explicit `visual_ready` (fonts/frame/media prepared), can be revoked with false at the same projection fence, and expires after ten seconds. The client renews every three seconds; capture admission and supervision must fail closed when it expires. Readiness never acknowledges media capture. The current kernel returns `recording_capture_unavailable` for start/stop: no recorder, MP4, clock, privacy test or recovery proof has been claimed.

LiveKit's SDK requires its short-lived, hidden, subscribe-only room JWT in the provider WSS signaling `access_token` query. This is the sole protocol exception. Provider hosts must come from trusted configuration, production requires TLS, and complete signaling URLs/tokens must never be persisted, logged or propagated in raw provider errors. Application purpose tickets and session cookies never enter URLs. Self-hosted LiveKit cannot revoke issued room tokens immediately; that capability remains false.

Private renderer assets are header-authorized against exact projected asset IDs and checksums. The client must verify fetched bytes before creating a local Blob URL. Chat, auth UI and host controls are outside the projection. Unknown policy/track, revocation, stale generation and altered output hashes fail closed. `recording.output` assets remain private; learner routes may read only after their existing immutable-release authorization, and cannot use preview readiness to bypass review.

Publication claims lock projects in sorted order, then renders/assets before learning takes track/lesson/draft locks. The claim is tied to the current transaction and cannot survive a commit, rollback, target edit or draft-version mismatch. Learning remains the single writer for immutable lesson/release publication. No auto-publish, original-file fallback, retention deletion or provider delivery is implemented by this kernel.
