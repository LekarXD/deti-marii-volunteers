# Recording kernel

Projects, takes, current privacy projections, monotonic renderer fences, scene history, render/review/publication records use PostgreSQL and the shared asset/job lifecycle. The owner needs explicit `recordings.manage`; exact render approval and learning publication additionally require `recordings.review` and `recordings.publish`. Room membership belongs to `studio`, and immutable lesson versions belong to `learning`.

The private renderer uses a one-use opaque orchestration ticket (three minutes) in `Authorization: Bearer`. Bootstrap consumes it and returns an independent two-hour opaque renderer access credential. Both are stored only as hashes and are bound to the take, room generation and current host auth session. The orchestration handoff must put the bootstrap ticket directly in browser memory through a private init binding; URLs, fragments, cookies, history and ordinary app providers are not credential channels. No ordinary HTTP endpoint issues bootstrap tickets. A leased internal capture job must fence before issuing one.

Projection hashes use SHA256 of RFC8785/JCS UTF-8 bytes, with pinned [rfc8785.py](https://github.com/trailofbits/rfc8785.py). They cover exactly `{scene,capture_plan,resolved_assets}` and exclude credentials and transport fields. This preserves ECMAScript numeric serialization, including integral floats, negative zero and exponent boundaries. Authorized renderer reconnects use header-only `POST /api/v1/recording-renderer/provider-grant`; it returns a fresh least-privilege room grant with the current projection fence, or explicit unavailability.

Each scene, allowlist, privacy or asset change increments `renderer_state_version`, clears readiness and appends its exact projection/hash. Readiness requires that fence/hash, approved policy, exact asset checksums, only allowlisted tracks, required ready tracks and the actual 1920x1080/DPR1 renderer profile. Readiness receipts carry a strictly increasing per-grant `readiness_sequence`: delayed older receipts are rejected and identical retries retain the original expiry. Issuing a new bootstrap ticket revokes all older grants for the take, clearing readiness. Readiness includes explicit `visual_ready` (fonts/frame/media prepared), can be revoked with false at the same projection fence, and expires after ten seconds. The client renews every three seconds; capture admission and supervision must fail closed when it expires. Readiness never acknowledges media capture. Start now queues `recording.capture` and returns `starting`; only the first real encoded and fsynced chunk permits `capturing`. Stop requests `stopping`; the worker finalizes the actual private tab, converts to H264/AAC MP4, checks the exact 1920x1080 profile/duration and fully decodes the output before creating a private preview asset. No renderer readiness receipt starts capture by itself.

LiveKit's SDK requires its short-lived, hidden, subscribe-only room JWT in the provider WSS signaling `access_token` query. This is the sole protocol exception. Provider hosts must come from trusted configuration, production requires TLS, and complete signaling URLs/tokens must never be persisted, logged or propagated in raw provider errors. Application purpose tickets and session cookies never enter URLs. Self-hosted LiveKit cannot revoke issued room tokens immediately; that capability remains false.

Private renderer assets are header-authorized against exact projected asset IDs and checksums. The client must verify fetched bytes before creating a local Blob URL. Chat, auth UI and host controls are outside the projection. Unknown policy/track, revocation, stale generation and altered output hashes fail closed. `recording.output` assets remain private; learner routes may read only after their existing immutable-release authorization, and cannot use preview readiness to bypass review.

Publication claims lock projects in sorted order, then renders/assets before learning takes track/lesson/draft locks. The claim is tied to the current transaction and cannot survive a commit, rollback, target edit or draft-version mismatch. Learning remains the single writer for immutable lesson/release publication. No auto-publish, original-file fallback, retention deletion or provider delivery is implemented by this kernel.


## Native isolated browser primitives

`browser_capture.cjs` implements the tested private channel. `__oporaTakeRendererBootstrap` requires a one-use challenge/nonce/consume handshake from exactly the designated Page/mainFrame/origin/`/recorder.html` with no query or fragment. Tickets remain in the runner closure; wrong pages/frames/replays never receive them. `installRequestBoundary` denies ordinary application APIs, third-party HTTP, child-frame navigation and unconfigured WebSockets. Only the configured provider origin may use its documented signaling exception. Camera and microphone are denied in Chrome permissions and by a non-configurable API override in every frame. No fake-device flag or native audio input is used.

The dedicated fresh browser profile is adjusted and checked at1920x1080/DPR1. Capture uses video-only `getDisplayMedia` with system audio excluded and requires `displaySurface=browser` and exact track dimensions, writes sequential bounded chunks to a private exclusive mode0600 spool, caps pending memory8MiB/disk500MiB/duration20min, and acknowledges start only after an actual encoded chunk is written. The final fsync/hash is separate from database job fencing, media validation, review and publication.

Run `scripts/recording_browser_smoke.cjs` explicitly with a pinned Playwright module and installed Chrome path. It creates only synthetic local pixels/tone and verifies wrong-frame/ordinary-auth/network/device denials. The initial native smoke established video capture and output-profile mechanics. Narration acceptance uses the exact approved RTC audio mixer below. This is mechanism proof, not a completed shared-Stage capture or long-recording/recovery acceptance. No runtime capability is enabled by this script.

## Native capture worker

Run `python -m app.worker.main --kind recording.capture` in the dedicated media runtime. Capture stays unavailable by default. Explicit opt-in requires `OPORA_CAPTURE_ENABLED=true`, `OPORA_CAPTURE_RENDERER_URL` pointing at the dedicated `/recorder.html`, `OPORA_CAPTURE_CHROME_PATH`, installed pinned Playwright/Node/ffmpeg/ffprobe, and configured LiveKit. HTTPS is required outside development; only loopback HTTP is admitted for development. Browser sandboxing is enabled; the runtime must support it.

`POST /recording-takes/{id}/policy` accepts the current take version, current scene revision, explicit approval, and complete track descriptors. The server compares them against the actual provider list and permits only the solo owner's tracks; another participant, missing/new track or stale scene blocks approval. Source IDs and kinds are never accepted as authority from the browser. Live multi-participant consent is unavailable until a separate consent policy exists. Project render discovery uses `GET /recording-projects/{id}/renders`; preview uses the existing private asset content endpoint.

The browser subprocess receives its one-use ticket only over stdin. No DB/provider key is inherited. The runner waits for the server's fresh exact readiness before starting native tab capture, emits start only after an encoded chunk, and remains supervised against auth, privacy, generation, readiness and job-lease revocation. Cancellation closes the private browser before a bounded process-group fallback. Raw WebM is a temporary bounded spool; the retained source is the validated composite MP4. No separate camera/screen source reconstruction or blind retry is promised.

The capture intent/checkpoint is committed before the browser starts. A worker restart with a launch/capture checkpoint fails the take as `capture_interrupted`; an unknown outcome cannot be silently replaced by a new recording. A stale lease cannot mark capture, create a render or publish an asset. A new take is the explicit recovery. Output assets remain private and require exact review plus the existing learning publication transaction.

For a same-policy owner scene revision, the server may authorize the prior approved frame for at most five seconds via `scene_transition`. The renderer must atomically swap to the verified new frame while retaining approved audio; media/privacy failure has no grace. Journal clocks for new frames are stamped at the actual ready receipt. Missing confirmation, checksum, clock, sequence or output decode fails closed.

`recording_pipeline_smoke.py` is an explicit local-only acceptance harness requiring a migrated `*_proof` database and `OPORA_RECORDING_SMOKE_DIST`. It creates its own loopback LiveKit/API, a fresh synthetic canvas+440Hz publisher and the real private renderer/worker. The static-scene run produced an inspected Opora Stage video at 1920x1080, H264/AAC, 4.013s and full decode. Its original tab audio is excluded from narration evidence; the final acceptance below supersedes that limitation. This is no claim of 20-minute capacity or production deployment. Those limits remain separate acceptance checks.

## Approved narration and final native acceptance

The retained composite uses exact browser Stage video plus a WebAudio mix of only the server-allowlisted RTC audio tracks already attached to SharedStage. `getDisplayMedia` requests `audio:false`; desktop/system/test-device audio is never a source. The mixer validates each unique Stage audio binding and live remote MediaStreamTrack, preserves those exact sources across authorized scene/asset swaps, and stops them at finalization. The worker independently checks provider participants/tracks once per second as well as renderer receipts, auth session, generation and lease. Unknown participants/publications, media disconnect or approval withdrawal abort the take without a render. A narrated take requires an approved active audio source.

API admission validates explicit opt-in, trusted renderer/RTC configuration. Chrome/node/ffmpeg/ffprobe executable validation happens only in the dedicated worker; the API image does not contain media tools. Claim acceptance and `capturing` still require a real encoded chunk.

The final teacher+presentation acceptance switched slide A→B and side→overlay during the same take. Its actual MP4 is 7.102s, 1920×1080, H264/AAC, fully decoded, with three exact journal projections. PCM inspection found the actual synthetic RTC 440Hz tone and 65 consecutive 100ms non-silent windows (minimum RMS 0.04922), including the handoff. Earlier native tab-audio files with generated test-device pulses are excluded as narration evidence. There is no claim of 20-minute capacity or production deployment.

The bounded scene handoff authorizes only the previous exact asset checksums at false readiness while the new asset is fetched/decoded. An unknown asset checksum, changed allowlist/policy, media failure or expiry is never tolerated. A handler rollback completes with its immutable claim values; it cannot leave an active take through an expired ORM Job reference. Auth advisory locks precede project/take locks, matching interactive and renderer requests.

The private Chrome lifecycle now uses an explicitly owned Playwright browser server bound to 127.0.0.1. Its random automation endpoint stays only in Node memory. A bounded graceful close falls back to killing only that owned Chromium process; stdin is closed before Node exits. Browser teardown has its own `closing_browser` checkpoint and timeout code, separate from ffmpeg validation. This fixes a 30-second-and-longer teardown hang that previously discarded an already fsynced source before the encoder ran. The native 30.862s Stage/audio output passed full decode after this correction.

`create_local_recording_fixture.py` creates only private loopback test configuration files (directory 0700, files 0600), fresh random keys and independently selected local ports. It starts no services and grants no devices. It accepts only the explicitly owned test PostgreSQL cluster 56147 and local renderer. Its JSON environment should be loaded directly into child-process environment without printing or shell evaluation.

The worker's automatic stop uses a monotonic clock at 1190s, ahead of the 1200s hard browser budget. Capability/take responses expose `max_duration_seconds` and a user-facing limit reason; completed takes preserve `stop_reason=duration_limit` or `owner_requested`. A real synthetic 5-second soft-deadline run produced a valid 5.294s H264/AAC preview after automatic stop, with full decode and no owner stop command. This tests the same soft-stop path without waiting 20 minutes or increasing any budget. The private subprocess also acknowledges actual owned-Chromium exit before encoding and closes its automation client/event loop explicitly.

## Current live room binding and reuse boundary

`POST /webinars/{id}/recording-project` binds an authorized current host to the exact existing live Studio session and scene revision. It creates no room, join grant, enrollment, attendance or notification. The recording project and live webinar retain independent identities; the renderer explicitly pins both its recording project and canonical `resource_kind/resource_id`. Current host authority, webinar publication, Studio generation and recording policy are checked again by the private renderer and worker. Live and solo takes use the same scene journal, capture process, audio mix, MP4 validation, asset registry, human review and learning publication transaction.

Consent covers only the host's exact provider-verified own camera/microphone/screen sources and projected materials. Current server-issued subscribe-only audience members with no publications are excluded, after checking immutable JWT metadata, current unrevoked login, active account and enrollment. Any audience publication, unknown participant/publication, expired membership or changed host fails closed. Chat/data and audience media never enter the composition. This does not implement multi-speaker consent.

The source provenance is OD (`curator-bot` HEAD `38c92cd`): LiveKit JWT/Twirp room transport is already a narrow port of `backend/services/lms_studio/livekit_auth.py` and `livekit_rooms.py`; canonical scene/composite presentation contracts and checkpoint/fencing patterns were adapted. The local capture adapter intentionally uses the common private SharedStage browser instead of copying OD's Egress process. OD `livekit_egress.py` requests `audio.capture_all`, `livekit_recording_pass.py` includes student-answer cameras, and `livekit_composite.py` falls back to raw tracks after failures. Its custom template uses URL signed-layout authorization and its `recorderTracks.js` attaches all room audio. These defaults cannot preserve the host-only approved-track policy and private challenge handshake unchanged. Existing custom-template Egress is a possible future production adapter to this same renderer, with those boundaries adapted; no second transport/encoder/retry engine was introduced for live binding. OD's Supabase lease RPC, Kinescope resumable delivery and raw-source fallback are not claimed as ported.

Frozen native acceptance at backend `2e7ead8` and renderer `9753e30` recorded 120.600s of actual SharedStage teacher+presentation output with A→B→A→B and side/overlay changes in one take. The H264/AAC 1920×1080 output fully decoded; the actual synthetic RTC 440Hz tone was present at early/middle/end and all 1200 consecutive 100ms windows were non-silent (minimum RMS 0.03808). Five exact journal events were retained. This is a local synthetic continuity proof, not a full 20-minute, staging, concurrency or production capacity proof. The soft 1190s stop/hard 1200s browser, memory8MiB and spool500MiB budgets remain enforced. The dedicated amd64 image could not execute on the available aarch64 host; container sandbox acceptance remains an environment gate.

Failure/restart recovery with a fresh fenced lease removes only the exact revoked hidden renderer grant identities for that take/generation. A stale lease cannot perform this provider mutation. This avoids waiting for LiveKit's transport-disconnect grace after an abruptly ended capture. Provider cleanup failure is recorded as `renderer_cleanup_pending`; the purpose grant and failed take remain revoked and cannot authorize a new capture. Native lease-loss recovery proved the actual capture child exited, no private participant remained active, and the interrupted take produced no render.
